Phase 3 Vision - App-Owned Price Cache And Country Food Baskets

Purpose

Phase 3 now has two connected objectives. First, the fixed food basket system must be removed and replaced by shared, country-level food basket configurations maintained directly in each country's Price Bulletin form. Second, because the planned external AWS price cache is not available, the application must own its own price cache database and keep it fresh through an asynchronous weekly rebuild process.

The Price Bulletin form should read from the app-owned cache by default. A separate refresh instance or worker connects to the Databridges API once per week, downloads the complete monthly price dataset ex novo, normalizes it, and atomically publishes a new cache version for the app. Users should not wait for full Databridges downloads during normal country selection.

Relationship To Earlier Phase 3 Draft

Architecture change: the previous Phase 3 draft assumed an existing external AWS database synchronized from Databridges every two weeks. That database is not available. Phase 3 now creates and owns the cache database inside the app architecture, with a weekly async full refresh job.

The user-facing food basket requirement remains the same: each country has a saved basket composed from Databridges commodities available for that country, with user-entered weights or quantities expressed in the units used by Databridges for those commodities. The saved basket is shared for that country until another authorized user changes it.

DataBridges API Basis

The implementation should use the official WFP VAM DataBridges Python client repository as the API reference. The repository documents an OpenAPI-generated Python package, data_bridges_client, requiring Python 3.10 or newer and OAuth-style application credentials. The relevant endpoints for Phase 3 include:

  • MarketPricesApi.market_prices_price_monthly_get for monthly commodity market price time series.
  • CommoditiesApi.commodities_list_get for country commodity metadata.
  • MarketsApi.markets_list_get and/or MarketsApi.markets_geo_json_list_get for market metadata.
  • CommodityUnitsApi.commodity_units_list_get and conversion endpoints for units.
  • CurrencyApi.currency_list_get when currency metadata is needed for price rows.

The monthly price endpoint returns monthly market price records and accepts filters such as country code, market ID, commodity ID, price type, currency ID, price flag, start date, end date, latest-value-only, page, output format, and environment. The app cache worker should page through results and respect Databridges rate limits and retry requirements.

Current Baseline

  • Country selection can be slow because Price Bulletin data is fetched live from Databridges.
  • The originally planned external AWS cache is unavailable.
  • Food basket composition is fixed or application-driven instead of manually configured per country.
  • Generated basket prices and charts do not yet depend on saved country basket definitions.

North Star

A VAM officer opens the Price Bulletin form and selects a country. The app responds quickly because all country metadata, commodities, units, markets, and monthly price rows come from the app-owned cache. The form shows cache freshness, the current active country basket, and any warnings from the latest weekly refresh.

If no basket exists for the selected country, the officer creates one by choosing commodities available in the cached Databridges metadata and entering weights or quantities in the displayed Databridges unit. If a basket exists, the officer sees the saved composition and can reopen the basket editor when a methodology change is needed. Saving creates a new country basket version that future bulletins use.

In the background, a weekly refresh worker downloads the full monthly price database from Databridges into staging tables. If validation passes, the app publishes the new cache version atomically. If the refresh fails, users keep working from the last successful cache version and see a clear freshness warning.

Core Product Changes

1. App-Owned Price Cache

The application will include its own durable cache database for Databridges monthly price data and supporting metadata. The Price Bulletin tool reads from this cache by default. Live Databridges calls are moved out of normal form loading and into controlled sync processes.

2. Weekly Asynchronous Full Refresh

A scheduled background worker runs once per week. It connects to Databridges using the official client, downloads the complete monthly price dataset ex novo, stores the result in staging tables, validates completeness and row quality, then promotes the new cache version.

The refresh must be non-blocking for users. Price Bulletin users continue reading from the currently active cache version while the new version is being built.

2a. GCP Beta Deployment Target

The beta deployment is on GCP, so Phase 3 should be designed for GCP-native infrastructure. The preferred beta shape is a managed relational cache such as Cloud SQL for PostgreSQL, plus a scheduled GCP worker such as a Cloud Scheduler-triggered Cloud Run job. Repository and worker boundaries should remain clean so the cache backend can change later if deployment requirements evolve.

3. Atomic Cache Publication

A failed refresh must not corrupt the active cache. The preferred approach is versioned cache snapshots: build a new version in staging, run validation, then update an active version pointer. Reads always use the active successful version.

4. Shared Country Food Baskets

The fixed global basket is removed. Each country has one active shared basket composed manually from the commodities available for that country in Databridges. Each item stores the commodity ID, commodity name snapshot, Databridges unit, and user-entered weight or quantity.

5. Basket-Driven Calculations And Charts

Price Bulletin basket price calculations and graphs use the active saved basket version. Missing basket components must be surfaced as warnings and must never be silently treated as zero.

Chart history must be truthful and readable. Food-basket and single-commodity charts may show prior-year and full five-year same-month overlays when the cache contains enough history; multi-commodity charts should prioritize current-period lines instead of crowding the page with repeated overlays.

5a. Exchange-Rate Usability

Exchange-rate sections are gated by both coverage and generic usability diagnostics. A complete official DataBridges series is not enough when it is official-only, near-static, and inconsistent with the local price scale. In that case the report should use a usable unofficial series or configured fallback source when available, otherwise omit FX and record the reason in report metadata.

6. Manual Latest Refresh

Manual latest refresh remains part of Phase 3. Country selection stays cache-only and must not call Databridges. Because a weekly cache can still be behind Databridges, users can explicitly click a Price Bulletin refresh action that checks the gap between the latest reportable cached basket month and the current month. The action fetches all priced commodities for the selected country, filters to actual or aggregate monthly rows, deduplicates against the active country cache, creates a new country-specific cache version when new usable rows exist, and activates that version for the selected country only.

7. Efficient Country-Scoped Retrieval

The refresh process may download and validate the complete price dataset, but the serving path must be optimized for the Price Bulletin workflow. Country selection and report generation should query by country, date range, commodity, market, and region using indexes and summary metadata. Refresh internals can be country-chunked for resumability, but the user-facing priority is fast, reliable country-level retrieval.

Primary User Journeys

Journey A - Weekly Cache Refresh

  1. The scheduler starts the weekly refresh worker.
  2. The worker authenticates to Databridges.
  3. The worker downloads commodities, units, markets, currencies, and monthly price rows.
  4. Rows are normalized into the app cache schema.
  5. The worker writes all rows into a new staging cache version.
  6. The app validates row counts, required fields, uniqueness, and country coverage.
  7. If validation passes, the new version becomes active.
  8. If validation fails, the old active version remains in service and admins see the failure.

Journey B - Price Bulletin From Cache

  1. User opens the Price Bulletin form and selects a country.
  2. The app loads country metadata and price availability from the active app cache.
  3. The app shows cache version, last successful refresh, and active country basket.
  4. User selects reporting period, regions, and output options.
  5. The app calculates the basket price from the saved country basket.
  6. The app generates graphs and report text using cached data and saved basket metadata.

Journey C - Create Or Modify A Country Basket

  1. User selects a country in the Price Bulletin form.
  2. The app shows the active basket or asks the user to create one.
  3. User opens the basket editor.
  4. User selects commodities from the cached Databridges commodity list.
  5. The form displays each selected commodity's Databridges unit.
  6. User enters weights or quantities and saves.
  7. The app validates and publishes a new basket version for the country.

In Scope

  • App-owned persistent price cache database.
  • Weekly asynchronous full refresh from Databridges.
  • Staging, validation, and atomic cache version promotion.
  • Admin-visible sync status, errors, and latest successful refresh timestamp.
  • Cache-first Price Bulletin country selection and data loading.
  • Shared country food basket editor, storage, versioning, and audit trail.
  • Basket-driven national and regional basket price calculations.
  • Basket graph updates, truthful history overlays, and missing-coverage warnings.
  • Exchange-rate usability checks and diagnostics for misleading official-only nominal rates.
  • Manual latest country refresh for the selected Price Bulletin country.
  • GCP beta deployment design for the cache database and weekly worker.

Out Of Scope

  • Using the unavailable external AWS cache database.
  • Writing data back to Databridges.
  • Replacing the full Streamlit frontend.
  • Making country baskets private to individual users.
  • Real-time continuous synchronization from Databridges.
  • Guaranteeing all Databridges domains beyond price data are cached in Phase 3.

Open Decisions

  • Who is allowed to edit shared country baskets: all users, admins, or country focal points?
  • Should scheduled weekly refresh publish only a complete global cache version, or allow per-country activation if one country fails?
  • Whether manual latest refresh should remain all priced commodities or later narrow to basket plus selected extras.
