Phase 3 Tech Stack - App-Owned Price Cache

Design Principles

  • Keep the existing Streamlit, FastAPI, Python, pandas, matplotlib, and DOCX stack.
  • Add an application-owned price cache database because the external AWS cache is unavailable.
  • Use a background worker or scheduled instance for weekly full Databridges refreshes.
  • Use staging tables and atomic promotion so failed refreshes do not break the app.
  • Keep Price Bulletin reads cache-first and fast.
  • Use the official DataBridges Python client as the API integration layer.
  • Store country food baskets as shared, versioned country configurations.

The current Streamlit-only runtime routes page requests through app/streamlit_backend/dispatcher.py, which mirrors the FastAPI routers in-process. Any FastAPI endpoint used by a Streamlit page must also be registered in this dispatcher and covered by dispatcher tests.

Database Choice

For the beta deployment, target GCP-native infrastructure. Prefer Cloud SQL for PostgreSQL for the app-owned price cache. The data is relational, time-series-like, and read by country, commodity, market, date, price type, and region. PostgreSQL also supports transactions, indexes, staging tables, and advisory locks well.

For local development and tests, SQLite can be used as a lightweight adapter if the repository interface stays the same. Do not build production code around SQLite-specific behavior.

The official client is an OpenAPI-generated Python package. It uses OAuth-style credentials through WfpApiToken and provides API classes for commodities, commodity units, markets, currencies, and market prices. The host and environment should be configurable because the repository documentation and existing local implementation reference different API gateway versions.

Weekly Refresh Worker

The refresh worker should run outside the request path on GCP. The preferred beta deployment is a Cloud Scheduler-triggered Cloud Run Job or equivalent worker container. The app should treat it as asynchronous infrastructure.

  1. Acquire a refresh lock so only one full refresh runs at a time.
  2. Create a new price_cache_versions row with status building.
  3. Authenticate to Databridges.
  4. Fetch metadata: commodities, units, markets, currencies.
  5. Fetch all monthly price pages. Prefer country-chunked ingestion if it improves resumability and progress reporting.
  6. Normalize all records into staging tables for the new cache version.
  7. Validate required fields, uniqueness, row counts, country coverage, and date ranges.
  8. Promote the version by updating price_cache_active_version in one transaction.
  9. Mark the previous active version as superseded.
  10. Retain a limited number of older versions for rollback and debugging.

Cache Validation Rules

  • Monthly price rows must have country, commodity, market, date, and price.
  • Commodity and market references in price rows should exist in the same cache version where possible.
  • Duplicate canonical keys should be rejected or deterministically collapsed before promotion.
  • Country row counts should be compared with the previous successful version and flagged for large unexplained drops.
  • The latest price date by country should be computed and stored.
  • Refresh failure must leave the active version untouched.

Food Basket Calculation

component_value = monthly_average_price_for_commodity * saved_weight_quantity
basket_price = sum(component_value for all available basket components)

Missing components must produce explicit coverage metadata. The calculation result should include total component count, available component count, missing commodity names, and whether the basket is partial for that month or region.

Manual Latest Refresh

Manual latest refresh remains enabled in Phase 3 behind MARKET_MONITOR_MANUAL_REFRESH_ENABLED. Country selection remains cache-only. The Price Bulletin form reads GET /market-monitor/countries/{country}/reportable-months to populate only basket-complete reference months. When the user clicks refresh, POST /market-monitor/countries/{country}/reportable-months/refresh fetches all priced commodities for the selected country from Databridges between the latest reportable cached month and the current month. New actual or aggregate rows are normalized, deduplicated, written into a manual_country_latest cache version, and activated for that country only. These reportable-month and refresh routes must work through both the FastAPI router and the Streamlit local dispatcher.

Tests

Unit Tests

  • Databridges adapter paginates until all pages are fetched.
  • Normalization maps monthly price fields into the cache schema.
  • Duplicate canonical keys are handled deterministically.
  • Refresh validation blocks missing required fields.
  • Basket validation rejects empty, duplicate, unknown, missing-unit, and non-positive items.
  • Basket calculation matches known weighted fixtures.

Integration Tests

  • Weekly refresh builds a new cache version and promotes it atomically.
  • Failed refresh leaves old active version readable.
  • Country selection reads from active cache and does not call Databridges.
  • Reference-month options are basket-aware reportable months only.
  • Manual latest refresh can promote a country-specific cache version without changing the global active pointer.
  • Basket edits by one user are visible to another user.
  • Generated reports record cache version and basket version.

Open Technical Decisions

  • Exact GCP resource choice and naming for Cloud SQL, scheduler, worker container, service accounts, and secrets.
  • Whether scheduled workers should activate a complete global cache version only or support per-country activation; manual latest refresh already uses country-specific activation.
  • Exact active-version retention and cleanup policy.
  • Whether manual latest refresh should remain all priced commodities or later narrow to basket plus selected extras.
